# Human-Agent Meeting

把当前任务看作一场 Human 与 Agent 的会议。散会时回顾真实发生的讨论，生成以决策为主、关键过程可回放的 Markdown 纪要。

这个 skill 是归档动作，只能由用户显式触发。不要在普通分析、讨论或任务结束时自行调用。

## 用户可以怎样触发

零参数调用：

```text
/human-agent-meeting
```

用户也可以用自然语言覆盖默认判断：

```text
/human-agent-meeting 话题用“Agent 会议纪要 Skill 设计”
/human-agent-meeting 保存到 ~/notes/meetings
/human-agent-meeting 拆成两份：产品决策、技术实现
```

不要要求用户学习 `--topic` 或 `--output-dir` 一类固定 CLI 参数。用户明确指定的话题、目录、语言和拆分方式优先于自动判断。

## 默认工作流

1. 回顾当前任务中可见的完整对话和实际证据。
2. 识别主要话题、会议状态、最终结论、决策、观点转折、未决问题和行动项。
3. 判断是一份单话题纪要，还是存在多个各自形成结论的独立话题。
4. 判断会议是否明确属于某个项目，并确定保存位置。
5. 检查目标文件是否已经存在，以及它是否属于当前这场会议。
6. 对凭证类信息强制脱敏。
7. 使用 `assets/meeting-notes-template.md` 生成纪要并直接写入。
8. 重新读取文件，检查结构、事实边界、脱敏和路径。
9. 在聊天中报告文件路径、会议状态、一句话结论和未决问题数量。

默认直接写入，不增加例行确认。只有关键歧义会改变归档结果时才询问用户。

## 事实边界

纪要只使用本次会议真实出现过的材料：

- 当前任务中的对话；
- 本次讨论期间实际读取或修改过的文件；
- 本次讨论期间实际执行过的命令及其结果；
- 本次讨论期间实际访问过的链接或外部资料；
- 为确定归档位置而读取的项目根目录、仓库名和当前工作目录。

不要在触发后为了让纪要更丰满而重新搜索、研究或运行新的技术验证。路径判断、同名检查和写后校验不算扩展调查。

保持事实的置信度：

- 已被证据支持的内容可以写成事实；
- 未经验证的判断标记为“判断”“假设”或“待验证”；
- 被后续讨论推翻的观点不能留在最终结论中；
- 无法从当前上下文获知的信息使用 `null`、写“未知”或直接省略，不能猜测。

## 划定会议边界

默认围绕触发时的单一主要话题生成一份纪要。把明显偏题、且没有独立结论的支线压缩放入相关讨论，不要让它取代主议题。

如果两个以上话题各自形成了独立结论，询问用户要合并还是拆分。用户选择拆分后，每个话题生成一份文件。不要默认把当前窗口里的所有内容塞进同一份文档。

## 判断项目归属

只有同时满足下面两个条件，会议才明确属于一个项目：

1. 能识别项目根目录，例如用户指定的目录、Git 根目录或明确的项目配置目录；
2. 讨论的主要话题确实与该项目的代码、产品或决策有关。

判断优先级：

1. 用户明确指定项目或目录；
2. 讨论持续读取、修改或验证某个项目；
3. 话题明确指向当前项目；
4. 只有当前工作目录但话题无关，不视为项目归属。

明确属于项目时，保存到：

```text
<project-root>/docs/meetings/YYYY-MM-DD/<topic>-会议纪要.md
```

项目归属不明确时，必须询问用户保存到哪里。用户选择的目录作为基础目录，在其中创建日期目录：

```text
<user-selected-directory>/YYYY-MM-DD/<topic>-会议纪要.md
```

如果用户明确给出完整 `.md` 文件路径，尊重该路径，不再追加默认层级。

日期使用触发时的本地日期。不要因为 Agent 恰好运行在某个仓库中，就把无关会议写进该仓库。

## 生成话题和文件名

从原始问题与最终目标中提炼具体、可检索的名词短语。中文话题通常控制在约 8～24 个字，但清晰度优先。

避免“问题讨论”“方案分析”“会议记录”一类空标题。清理控制字符、路径分隔符以及 `< > : " / \\ | ? *` 等不适合文件名的字符，合并多余空白，去掉结尾句号。只有多个标题会造成实质性归档差异时才询问用户。

日期只放在目录中，不重复放入文件名。

## 处理同名文件和会议修订

不要静默覆盖文件。

- 如果当前上下文已经生成过一份纪要，而且能明确识别为同一场会议，再次触发时默认重整并更新原文件。
- 更新时重新审视全文，不要只在末尾机械追加。增加 `revision`，刷新 `updated`。
- 后续被推翻的结论移出“结论摘要”，放入“被否决的方案”或讨论回放。
- 如果同名文件存在但无法确认属于同一场会议，询问用户要更新原文件还是创建 `<topic>-会议纪要-2.md`。

## 会议状态

Frontmatter 的 `status` 只使用这些稳定值：

- `concluded`：已达成结论；
- `partially_concluded`：部分达成结论；
- `unresolved`：未达成结论；
- `blocked`：因外部条件阻塞。

没有最终结论也要生成纪要。此时把“结论摘要”写成当前判断，记录已经排除的方向、尚存分歧和下一步验证动作。不要为了文档完整而虚构共识。

## 参与者与语言

讨论回放使用稳定角色名 `Human` 和 `Agent`。在 Frontmatter 中仅在可靠时补充工具名或模型名；不知道具体模型就不要猜。多个 Agent 用工具名或可识别的子 Agent 名区分。

正文跟随会议主要语言。中英混合时以用户的主要语言为主，代码、命令、路径、API 名称和专有名词保持原样。Frontmatter 使用模板中的固定英文键和值。用户明确指定输出语言时按用户要求执行。

## 关键讨论回放

记录观点转折，不做逐轮聊天流水账：

- 谁提出了初始判断；
- Human 如何质疑、补充或改变约束；
- Agent 如何回应和修正；
- 哪个理由造成关键转折；
- 最终怎样形成共识。

删除寒暄、重复表达和无效试探。必要时引用一句关键原话，但长对话以准确概括为主。曾提出但未被采纳的观点必须明确标成“未采纳”或“已推翻”。

## 原始问题、决策与行动项

在“原始问题”中保留用户最初定义议题的关键原话：短问题可完整引用，长问题只引用最能定义议题的部分。经过讨论后目标发生变化时，再写“最终目标”；没有变化则省略该小节。

每项决策至少说明：决定、理由、约束与前提、被否决的方案、影响。没有实际内容的字段可以写“无”，不要用套话填满模板。

行动项只记录对话中明确形成的动作。负责人和期限没有被明确指定时写“未指定”，不能替参与者安排工作或编造日期。

参考资料只列本次讨论实际使用过的文件、链接、命令或证据。没有参考资料时写“无”。

## 敏感信息

API Key、access token、密码、Cookie、私钥、连接串中的凭证等秘密不得写入纪要。用 `[REDACTED: token]`、`[REDACTED: password]` 等占位符保留语义，并把 Frontmatter 的 `redacted` 设为 `true`。

其他个人隐私、内部地址和业务数据不要擅自扩大脱敏范围；用户明确要求时再处理。脱敏不能破坏技术结论，例如可以写“认证因 Token 失效而失败”，但不能复制 Token 原值。

## 使用模板

读取并遵循 `assets/meeting-notes-template.md`。保留模板的主章节顺序，让读者先看到结论，再选择是否回放讨论。

Frontmatter 要保持合法 YAML：

- `date` 和 `updated` 使用 ISO 8601；
- `status` 使用固定枚举；
- `project` 未知时使用 `null`；
- `participants` 使用对象列表，不要把带冒号的字符串写成含义不明的 YAML；
- `tags` 只从实际话题提取；
- `revision` 初次为 `1`；
- `redacted` 是布尔值。

## 写后校验

写入后重新读取文件并确认：

- 路径符合项目归属、日期目录和文件名规则；
- YAML Frontmatter 能正常解析；
- 结论与当前会议最终共识一致；
- 被推翻的旧观点没有伪装成最终结论；
- 关键质疑、修正和转折能够回放；
- 未验证内容保留不确定性；
- 凭证原值没有落盘；
- 行动项的负责人和期限没有被虚构；
- 引用的文件、链接和命令确实在本次讨论中出现过。

## 最终回复

写入成功后简短报告：

```text
会议纪要：<absolute-path>
会议状态：<中文状态>
结论：<一句话结论>
未决问题：<数量>
```

如果因为项目归属、多话题拆分或文件冲突而等待用户决定，明确说明唯一阻塞点，只问解决该阻塞所需的一个问题。
